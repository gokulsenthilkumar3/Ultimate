## Finish trusted signing

1. Obtain an individual code-signing certificate with the verified name matching **Gokul Senthilkumar**. A provider must verify the applicant's identity; enter identity documents only in its own secure verification process. For example, [SSL.com IV Code Signing](https://www.ssl.com/products/software-integrity/code-signing/iv/) supports individual names and requires government-issued identity verification. Its advertised one-year certificate price at review was USD 129; secure hardware/cloud key storage and signing subscriptions are additional costs. Confirm current country eligibility, total fees and terms before purchasing.
2. Choose hardware-token or cloud-HSM signing. Public code-signing private keys are generally hardware protected; do not assume a newly issued certificate can be exported to PFX. Provider-specific cloud signing requires its supported tooling and a reviewed electron-builder signing hook. Existing CSC_LINK/CSC_KEY_PASSWORD settings apply only when an appropriate exportable certificate is available. Keep credentials in ignored local environments or repository secrets, never in package.json, the graph or this guide.
3. Configure the actual signing identity using the pinned electron-builder version's supported options. For version 26, `win.signtoolOptions.certificateSubjectName` selects a certificate in the Windows store and `win.signtoolOptions.publisherName` describes the exact certificate name for update verification. Configure these only after issuance; setting publisherName alone does not sign an executable. See the [version 26 Windows signing guide](https://www.electron.build/v26/docs/features/code-signing/code-signing-win/).
4. Build a new version with code signing required (`win.forceCodeSigning: true` for the signed build). Timestamp signatures using the provider's supported timestamp service. Verify both the installed application executable and the installer using `Get-AuthenticodeSignature`; require Status Valid and the expected signer identity. A checksum alone is insufficient.
5. In GitHub Actions, enable `WINDOWS_SIGNING_REQUIRED=true` once the chosen signing integration is configured. The existing workflow blocks publishing an installer whose signature is not Valid when this variable is enabled. This workflow still requires its pending source changes to be merged before it is available on GitHub.
6. Test install/upgrade, regenerate checksums and publish a new release. Do not overwrite the existing public installer or describe the current unsigned build as verified.

Microsoft's [production signing guidance](https://learn.microsoft.com/en-us/windows/msix/package/sign-msix-package-guide) currently limits Artifact Signing enrollment for individual developers to the USA and Canada; do not assume eligibility in another country. Self-signed certificates are intended for explicitly trusted test environments, not broad public publisher verification. SmartScreen reputation may still need to develop after valid signing.
