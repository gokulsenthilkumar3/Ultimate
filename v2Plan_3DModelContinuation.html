Key invariants across the whole repo
metricsToBlendshapes.js is pure — no side effects
Takes a metric object, returns a blendshape weight object. No DOM access, no store reads, no async. Testable in isolation with 100% coverage requirement.
3D layer never reads from stores directly
AvatarModel.jsx receives blendshapeWeights as a prop. The store → computation → prop chain is explicit and traceable. No coupling between the 3D scene and business logic.
Every GLB loads with useGLTF + Suspense
All model loading is suspense-based. A glass-surface skeleton shimmer shows while loading. No blank black viewport ever.

Fallback weight computation — formula table
When a metric is absent, these fallback values are computed from available data and normalized before mapping:

waist_cm_est = 0.447 × height_cm + 0.294 × weight_kg − 28.4 (M) | − 31.6 (F)
hip_cm_est = 0.541 × waist + 0.308 × weight + 12.3
thigh_cm_est = 0.268 × hip + 0.189 × weight + 8.1
calf_cm_est = 0.38 × thigh − 4.2
upper_arm_cm_est = 0.29 × weight + 5.8 (M) | 0.27 × weight + 5.1 (F)
shoulder_width_est = height × 0.259 (M) | height × 0.228 (F)
body_fat_est = BMI-based: (1.39 × BMI) + (0.16 × age) − (10.34 × isMale) − 9.0
breast_vol_step = round((chest_cm − underbust_cm − 12) / 4) clamped 0–5
All formulas clamped to population min/max before normalization

Arms: upper_arm_cm · forearm_cm · wrist_cm · arm_length_cm
Legs: thigh_cm · knee_cm · calf_cm · ankle_cm · inseam_cm
Face: face_shape · neck_cm · head_size

Actions: setMetric(key, value) · setMetrics(obj) · resetToDefaults(gender) · syncFromDB() · saveToDB()
useGoalMetrics — inherits + overrides
Same shape as useCurrentMetrics but all values nullable. On read: goalValue ?? currentValue (goal inherits current if unset — means "no change planned for this zone").

Extra fields: goal_type ('workout'|'diet'|'surgery'|'style') · target_date · surgery_type · notes

Key action: getEffectiveGoal() — returns merged object of goal values, falling back to current values for any null goal metric. This is what drives the goal avatar.

Data flow — metric change to avatar morph
1
User moves a slider
MetricSlider calls setMetric('waist_cm', 82) on useCurrentMetrics store.
2
useMetricMorph hook reacts
Subscribes to store changes. On change, runs metricsToBlendshapes(metrics, gender) → returns new weight object.
3
GSAP tween fires
morphTween(mesh, currentWeights, targetWeights, 0.6s) — only changed targets are tweened. Others hold position.
4
Three.js renders the frame
On each RAF, mesh.morphTargetInfluences are read by the GPU. Vertex positions interpolate between base mesh and morph target.
5
DB sync (debounced 2s)
After 2s of inactivity, saveToDB() fires — writes the full metric object to user_metrics table. No per-keystroke DB writes.

A scrollable horizontal row of zone tabs: Core · Torso · Arms · Legs · Face · Hair · Muscle · Style. Tapping a zone expands its metric list below. Each zone has an icon + label + a small completeness dot (filled = has data, empty = default/estimated).

Step-by-step asset production pipeline
1
MakeHuman — create base characters
Open MakeHuman. Set gender to Male. Set all sliders to exact population-median values (BMI 25, age 28, European ethnicity as neutral starting point). Export → MHX2 format with "Include body mesh", "Include skeleton". Save as male_median.mhx2. Repeat for Female. These are your neutral default avatars.
2
Blender — import via MPFB2
Install MPFB2 (MakeHuman Plugin For Blender, v2). Import the .mhx2 file. This gives you the base mesh with the full skeleton and all MakeHuman targets accessible as shape keys in Blender. You will see them in the Shape Keys panel on the mesh object.
3
Blender — select and rename shape keys
From the Shape Keys list, identify the keys matching your blendshape spec (waist_wide, hip_wide, etc.). MakeHuman uses its own naming — map to yours. Delete shape keys you don't need (keeps GLB lean). Rename the remaining ones to match the spec exactly. This is the naming contract between the asset and the code.
4
Blender — skin material setup
Assign a Principled BSDF material. Roughness: 0.6. Specular: 0.3. Subsurface: 0.05 (tiny amount — enough to soften edges). Subsurface Color: #FF8866. Use your 4K skin texture as Base Color. Plug normal map into Normal input. Plug roughness map into Roughness. Mark face mesh as a separate material slot — it gets its own SSS values later in the shader.
5
Blender — idle animation bake
Create a single looping action called "idle" (120 frames at 24fps = 5s loop). Keys: chest/abdomen Y-scale oscillates ±0.003 on sine, left/right hip X offset ±0.001 every 60 frames, head Y-rotation ±2° over 120 frames. Make it subtle — barely perceptible. Export with this action included.
6
Blender — GLB export settings
File → Export → glTF 2.0 (.glb). Settings: Include: Selected Objects, Shape Keys, Skinning, Animations. Geometry: Apply Modifiers ON, UVs ON, Normals ON, Tangents OFF, Vertex Colors OFF (if unused). Animation: Limit to Playback Range ON, Always Sample Animations ON. Compression: Draco OFF (causes morph target issues). Output: public/models/male_base.glb.
7
Verification in Three.js
Load the GLB with GLTFLoader in a test scene. Log mesh.morphTargetDictionary — verify all expected target names are present. Set each to 1.0 one at a time and verify the correct zone deforms. Set back to 0.0. If any target is missing or misnamed, fix in Blender and re-export. This is the acceptance test before any code is written against the asset.
8
Hair assets — separate GLBs
Each hair style is a separate .blend file. The hair mesh is rigged to only the head bone (so it moves with head animation). No shape keys needed — color is set at runtime via material.color. Export each as a separate GLB. Name: hair_{style}_{gender}.glb. Hair GLBs are small (<200KB each) — load on demand, not at startup.
9
Texture compression for web
Use gltf-transform CLI to apply WebP texture compression to the final GLBs: gltf-transform webp male_base.glb male_base_web.glb --quality 85. Reduces 4K texture from ~6MB to ~1.2MB with near-identical visual quality. Separately keep the uncompressed version as source-of-truth.
Every animation in the app — what it is, how it moves
Morph target transitions (body shape changes)
Library: GSAP
Duration: 0.6s
Ease: power2.inOut
How: gsap.to(mesh.morphTargetInfluences, { [targetIndex]: newWeight, duration: 0.6, ease: 'power2.inOut' })
Rule: Only changed targets tween. Unchanged targets do not animate. Prevents unnecessary GPU work.
Batch: Multiple metrics changing simultaneously (e.g. "Apply all") → all tweens start at same timestamp. Body reshapes holistically.
Mode switch — Current ↔ Goal ↔ Compare
Sequence: Avatar scales to 0.95 (100ms) → cross-dissolve opacity 0→1 (200ms) with new blendshape weights applied during opacity 0 → scale back to 1.0 (150ms).
Simultaneous: Background color transitions (CSS transition 700ms). GlassPill selected indicator slides (Framer Motion layoutId, 300ms spring).
Total perceived duration: ~450ms
UI panel open / close
Open: y: [40px→0], opacity: [0→1], blur: [6px→0] — Framer Motion spring(stiffness:280, damping:30)
Close: y: [0→40px], opacity: [1→0] — spring(stiffness:260, damping:28)
Sheet (bottom): y: ['100%'→'0%'] — spring(stiffness:300, damping:32). Drag gesture handled by Framer Motion drag constraints.
Metric value number display
On change: Number rolls up/down from old value to new over 0.4s using react-countup with easeInOutQuad. For sliders this is throttled — only animates on mouse-up, not on every drag tick (too distracting).
Camera orbit (OrbitControls)
enableDamping: true, dampingFactor: 0.06
Auto-rotate: autoRotate: true (0.003 rad/s) when idle >8s. Stops immediately on any user interaction.
Camera position changes (e.g. zoom to waist zone on tap): GSAP tweens camera.position and controls.target over 0.7s with power2.inOut. Never snaps.
Cursor parallax (desktop only)
Effect: Avatar head tracks cursor ±8° Y rotation. Camera lean ±2° X tilt. Both use lerp with factor 0.04 (very smooth lag).
Implementation: useCursorParallax hook — on mousemove, calculates normalised cursor offset from center, lerps the avatar's head bone rotation and the camera X in useFrame.
Disabled on touch devices.
Zone glow on slider drag
When the user is actively dragging a metric slider, the corresponding body mesh zone gets a warm vertex-color overlay via heatmap.frag.glsl uniform: uZoneHighlight = 1.0 fades in over 0.2s, returns to 0.0 over 0.4s on release. Color: rgba(245, 158, 11, 0.25) — warm amber.
Idle breathing (always-on)
AnimationMixer plays the "idle" action from the GLB in an infinite loop. Weight: 1.0 at all times. Does not conflict with morph target changes because it's skeleton-based (chest bone scale), not morph-based. Pause only on goal-achieved celebration animation.
Performance rules — non-negotiable
GPU tier detection → rendering profile
Use detect-gpu library on app load. Results in 3 tiers:

Tier 3 (high-end): Full post-processing (N8AO + SMAA + Bloom + ToneMapping + Vignette + DepthOfField on idle). dpr: min(window.devicePixelRatio, 2.0). Full HDRI. Full shadows.

Tier 2 (mid): N8AO (halfRes: true) + SMAA + Bloom + ToneMapping. No DepthOfField. dpr: 1.5. HDRI at half resolution. Shadow map 1024.

Tier 1 (low): No post-processing. MeshStandardMaterial only. dpr: 1.0. Three-point lighting only. Idle animation disabled if FPS < 30. Hair asset poly-count halved.
Asset loading strategy
Body GLB: Preloaded immediately on app start (largest, most critical asset).
Hair GLBs: Load only the currently-selected style. Swap on selection. Cache in memory — don't reload on re-select.
Clothing GLBs: Lazy-loaded on first outfit selection. All outfit variants preloaded silently after body GLB is ready.
HDR: Load at startup. Compress to 512px if Tier 1.
Loading state: Framer-animated skeleton shimmer (glass surface with animated gradient) until body GLB is ready. Never black screen.
Morph target computation throttle
metricsToBlendshapes() is called at most once per slider drag event (not per pixel). Throttled with requestAnimationFrame — one computation per frame maximum during drag. On slider release: final value computed and GSAP tween starts. No redundant re-computations mid-tween.
Dual canvas (compare mode) performance
Two WebGL contexts have a GPU memory cost. Rules:
— Compare mode uses shared scene objects (lights, HDRI) where possible
— Post-processing runs on both canvases at Tier 2 settings only (never Tier 3 in compare mode)
— Hair and clothing assets shared by reference between both contexts
— FPS target in compare mode: 30fps (not 60fps) — body shape fidelity matters more than smoothness here

Scoring rubric — how 9.5/10 is reached
3D model accuracy (3 points): Does it look like you when you enter your measurements? 1pt = rough silhouette. 2pt = proportions correct in most zones. 3pt = every zone responds correctly to its metric.

Dual self system (2 points): Does the Current vs Goal comparison work meaningfully? 1pt = two different states visible. 2pt = seamless transition, diff heatmap, goal type selector all working.

UI/UX quality (2 points): Does it feel premium? 1pt = functional and clean. 2pt = Apple/Lusion-level — glass surfaces, spring motion, micro-interactions all present.

Metric completeness + graceful degradation (1.5 points): Does every metric make a visible difference? Do missing metrics never break anything?

Rendering quality (1 point): HDRI lighting, N8AO, correct skin material — does the model look cinematic?

Performance (0.5 points): 60fps on desktop, no loading jank, GPU-tier adaptive.
