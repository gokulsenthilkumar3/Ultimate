What this plan delivers
The fundamental contract of this app
Whatever you look like in the real world — your height, weight, body shape, skin tone, face, hair — the 3D model must reflect that. Not approximately. Not generically. Actually you.

Every metric you add improves a specific zone. Every missing metric falls back to a sensible default — never breaks anything else.
No compromises
Core principles (rules that govern every decision)
Graceful degradation — always
If hair color is missing → black. If thigh circumference is missing → derived from weight + height. If everything is missing → gender-appropriate population-average defaults. The model ALWAYS renders. Never broken, never empty.
Progressive precision
The more metrics a user adds, the more accurate the avatar. Empty zones are visually indicated (subtle desaturation or a soft glow) — not broken. Each metric input triggers an instant animated morph on that body zone only.
Dual state — Current Self + Goal Self
Two completely independent metric stores. Two independent 3D model states. The user switches between them, or views them side-by-side. Goal state metrics are editable separately from current state metrics at all times.
Gender defines the mesh, not just a texture
Male and female are different GLB files with different blendshape sets, different fat distribution logic, different shoulder/hip ratios. Choosing gender at profile setup loads the correct base mesh. It never changes mid-session.
The 3D scene IS the app
Following Lusion's philosophy: there is no "3D widget inside a page." The 3D canvas is the entire viewport. UI elements float over it as translucent layers (Apple Liquid Glass). The model is always present, always interactive.

Design contract for metrics
Every metric maps to exactly one or more blendshape targets. If a metric is absent, a default value is calculated from existing metrics using a fallback formula. The 3D model never waits for all metrics — it renders with whatever it has.

Fallback formula — what happens when a metric is missing
Height + Weight → BMI → baseline fullness (always available after first two metrics)
Waist missing → estimated from: 0.447 × height + 0.294 × weight − 28.4 (Rexford formula, R²=0.81)
Hip missing → estimated from: 0.541 × waist + 0.308 × weight + 12.3
Thigh missing → estimated from: 0.268 × hip + 0.189 × weight + 8.1
Calf missing → estimated from: 0.38 × thigh − 4.2
Upper arm missing → estimated from: 0.29 × weight + 5.8 (gender-adjusted)
Shoulder width missing → M: height × 0.259, F: height × 0.228
Hair color missing → black (#1a0a00)
Face shape missing → oval (most common, neutral)
Skin tone missing → mid-warm neutral (#C68642)
All missing (first launch) → WHO population-median for entered gender + age 25
GLB asset architecture
Two base meshes — not one
Critical change
male_base.glb — built in MakeHuman, exported via MPFB (MakeHuman Plugin for Blender). Contains:
— 40+ morph targets (blendshapes) for body shape dimensions
— 8 morph targets for muscle definition zones
— Separate mesh layers: body skin, underwear, casual wear, sport wear
— Rigged skeleton with 54 joints for idle animation
— UV-mapped skin texture atlas (4K) with normal + roughness maps

female_base.glb — same structure, different topology:
— Different shoulder/hip ratio baseline
— Breast volume blendshape (controlled by chest circumference + cup size)
— Gynoid fat distribution (fat deposits lower body preferentially)
— Different waist-hip ratio range
— Same 54-joint skeleton (compatible animations)
Blendshape naming convention — the full list
Every blendshape follows: zone_property_direction

Body scale: height_tall, height_short, weight_heavy, weight_light
Torso: waist_wide, waist_narrow, hip_wide, hip_narrow, chest_large, chest_flat, shoulder_wide, shoulder_narrow, torso_long, torso_short
Fat distribution: belly_large, belly_flat, lovehandles_present, lovehandles_flat, thigh_fat_large, thigh_fat_small
Muscle: chest_muscle_defined, arm_muscle_defined, leg_muscle_defined, back_wide, abs_visible
Limbs: arm_long, arm_short, leg_long, leg_short, thigh_wide, thigh_narrow, calf_wide, calf_narrow
Face: face_round, face_square, face_oval, face_heart, face_diamond, neck_wide, neck_narrow
Age: age_young, age_middle, age_senior (affects posture, skin, muscle tone)
Female-specific: breast_volume_0 through breast_volume_5, hip_gynoid_wide
Male-specific: chest_pectoral_defined, beard_volume (face mesh)
Hair system — separate from body mesh
Hair is a separate GLB or mesh group loaded on demand, parented to the head bone.

Variants (pre-built assets):
— bald / buzz cut / short crop / medium / long straight / long wavy / long curly / afro / braids (F) / bun (F) / undercut (M) / fade (M) / medium textured (M)

Color system: Each hair mesh has a single MeshStandardMaterial with color property. Color is set programmatically at runtime from the user's hair color selection. No texture swap needed — just material.color.

Facial hair (M): Separate facial hair mesh overlay. Variants: none / stubble / goatee / short beard / full beard. Also color-matched at runtime.
Clothing / outfit layers
Outfit is a separate set of mesh layers that sit on top of the body mesh. They are toggled via visibility, not re-loaded.

Layer stack (bottom to top):
1. Body skin (always visible — clipped by clothing above)
2. Underwear layer — gender-appropriate, always tasteful, not explicit. Male: fitted briefs/boxers. Female: bra + briefs. Sized dynamically to body proportions via vertex skinning.
3. Casual wear — t-shirt, jeans/leggings. Selectable color.
4. Sport wear — compression shirt/leggings. Shows muscle definition better.
5. Accessories — glasses mesh, watch mesh, jewelry (optional future)

Default for new user: Underwear layer only. User can switch freely.
Idle animation + breathing
The model is never completely static. An idle animation loop is baked into the GLB:
— Breathing: chest/abdomen scale oscillates ±0.3% over 4s sine wave
— Subtle weight shift: left/right hip offset ±0.1 every 8s
— Head micro-movement: ±2° Y rotation over 12s (barely perceptible)

These are driven by AnimationMixer in Three.js. They make the model feel alive and real.
The pipeline — how a number becomes a 3D shape change
Pipeline overview
Step 1 — Normalize: Every raw metric is normalized to 0→1 relative to population min/max for that gender+age group. (Height 140cm→210cm maps to 0→1. Waist 55cm→140cm maps to 0→1.)

Step 2 — Blendshape weight calculation: Each normalized metric drives one or more blendshape weights via a piecewise linear or polynomial function. Multiple metrics can influence the same blendshape (additive, clamped 0→1).

Step 3 — Apply to morphTargetInfluences: mesh.morphTargetInfluences[targetIndex] = calculatedWeight. Three.js handles the actual vertex interpolation.

Step 4 — GSAP tween: Changes don't snap — they animate over 0.4–0.8s with ease. The user sees the body shape change smoothly when they adjust a slider.
Exact mapping — metric to blendshape (selected examples, full table in data sheet)
Height: Controls global scale via Object3D.scale.set(heightFactor, heightFactor, heightFactor). heightFactor = 0.75 + (normalized_height × 0.5). Simultaneously applies to torso_long/torso_short and leg_long/leg_short blendshapes for proportionate scaling.

Weight: Drives: weight_heavy (0→1), belly_large (threshold-gated above BMI 25), lovehandles_present (threshold-gated above BMI 28). Also adjusts all limb circumference fallback estimates.

Waist circumference: Primary driver of waist_wide/waist_narrow. Also cross-correlates: if waist > hip (android shape), belly_large gets +0.2 bonus. If hip > waist × 1.35 (gynoid shape), hip_gynoid_wide gets +0.3.

Hip circumference: Drives hip_wide/hip_narrow and thigh_fat_large (because hip width correlates with thigh girth in gynoid distribution). Gender-split: female baseline hip is wider at same normalized value.

Chest circumference: Male: drives chest_pectoral_defined (partial — combined with muscularity slider). Female: drives breast_volume_0 through breast_volume_5 via 6-step piecewise mapping based on circumference difference (bust−underbust).

Body fat % → shape distribution: Below 15% (M) / 22% (F): muscle definition visible (abs_visible=1, chest_muscle_defined scaling up). 15–25% (M) / 22–32% (F): average. Above 25% (M) / 32% (F): belly_large increases, lovehandles activate, thigh_fat increases. This is what makes "same weight, different fat%" look genuinely different.

Age: Affects: age_young/age_middle/age_senior morphs (posture shifts). Also shifts roughness on skin material (older → higher roughness, lower metallicity). Subtle wrinkle normal map blend-in above age 45.

Muscle sliders (0–100): Each zone independently drives its definition blendshape. At 0: soft, rounded. At 100: defined musculature. These stack on top of the anthropometric shape — so a high-body-fat user can have muscle sliders at 50 and see bulk, while a lean user at 50 sees cut definition.
Shape classification — body type detection for UI feedback
From waist + hip + chest metrics, the system automatically classifies:
Male: Ectomorph / Mesomorph / Endomorph / Athletic V-taper / Rectangle
Female: Pear / Apple / Hourglass / Rectangle / Inverted triangle

This label is shown as a subtle badge in the UI (not judgemental — purely informational). It also helps the goal system suggest relevant workout/diet types.
The rendering stack — from GLB to Apple/Lusion quality
Layer 1 — environment & lighting
HDRI environment map
HDR file: "photo_studio_01" or "studio_small" from Poly Haven (CC0 licensed). Loaded via pmremGenerator → scene.environment. Provides realistic ambient reflections on skin.

Key light: DirectionalLight, intensity 1.2, position [3, 5, 3] — slightly above and to the right. Casts soft shadows (shadow.mapSize 2048).

Fill light: DirectionalLight, intensity 0.4, position [−3, 2, −1]. No shadows. Prevents harsh falloff.

Rim light: DirectionalLight, intensity 0.3, position [0, 2, −5]. Behind-left of model. Creates the separation from background that gives depth.

Background: NOT the HDRI — transparent/dark. The background is a custom Three.js shader (animated aurora / deep space particle field). The model floats in cinematic space.
Skin material — MeshStandardMaterial + custom touches
Base: MeshStandardMaterial. roughness: 0.6, metalness: 0.0.

Skin subsurface scattering (SSS) approximation: A thin layer of MeshPhysicalMaterial with transmission: 0.05, thickness: 0.3, attenuationColor: #ff8866 on face/hands/ears only. This makes skin translucent in a realistic way where light passes through (ears glow slightly, nose bridge softens). Full SSS shaders are too expensive — this is the right approximation for web.

Skin texture atlas: 4K diffuse map, 2K normal map (pore detail), 1K roughness map (shinier on nose/forehead, matte on cheeks/body). These textures should be swapped for 6 ethnicity variants from a library like Renderpeople or custom-made.

Tone mapping: ACESFilmicToneMapping + exposure 1.1. This is the Hollywood standard for making skin look cinematic.
Layer 2 — post-processing
Effect composer chain (order matters)
1. N8AO (ambient occlusion): halfRes: true, aoRadius: 5, intensity: 1.5, color: black. Darkens armpits, groin, neck underside, knuckles. Adds massive depth without performance cost. Use N8AO over SSAO — it's more stable.

2. SMAA (antialiasing): Quality: High. Replaces WebGL's MSAA which doesn't work with post-processing.

3. Bloom: luminanceThreshold: 0.8, luminanceSmoothing: 0.025, intensity: 0.3. Very subtle — just catches skin highlights and rim light edges. Never bloom the whole model.

4. ToneMapping: ACESFilmic via ToneMappingEffect. Exposure: 1.1.

5. Vignette: offset: 0.5, darkness: 0.3. Focuses eye toward the model center.

6. DepthOfField (optional, on idle): focusDistance: 0.0, focalLength: 0.02, bokehScale: 2.0. Blurs the background particle field. Deactivate during user interaction for performance.
Layer 3 — background scene (the Lusion touch)
Animated background shader
Behind the model (and behind the UI layers) lives a full-screen custom fragment shader running on a plane geometry that fills the canvas. It creates depth and premium atmosphere without distracting from the model.

Option A — Deep space / aurora: Procedural noise-based aurora borealis. Slow drifting bands of deep indigo, violet, teal. Very low frequency — changes over 60s. Looks extraordinary on dark displays.

Option B — Studio gradient + dust: Dark charcoal radial gradient (center slightly lighter). Floating fine particle dust lit from above. Premium studio photography feel.

The background responds to model state: Current Self → neutral indigo/grey. Goal Self → warm amber-gold tones. Comparison mode → split — left side current colours, right side goal colours. This is subtle but powerfully communicates which state you're looking at.
Performance budget
Desktop target: 60fps, 1440p, full post-processing chain.
Laptop target: 60fps, 1080p, N8AO at halfRes, no DepthOfField.
Mobile/low-end: 30fps target, no post-processing, lower poly hair, disable idle animation if <30fps detected. GPU tier detection via detect-gpu library → automatically selects rendering profile.
Design language — Apple Liquid Glass + Lusion motion
What "Apple + Lusion" actually means for this app
From Apple Liquid Glass: Translucent surfaces that refract what's behind them. All UI panels, controls, and overlays appear as if made of backlit frosted glass floating above the 3D scene. Light from the 3D scene bleeds through and shifts the panel tone dynamically. Controls feel physical — pressing a button has weight.

From Lusion: The 3D scene is narrative, not just decoration. Every UI interaction causes a visual response in the 3D space. Mouse/cursor position subtly rotates the avatar. Scrolling through metrics creates a camera parallax. The model is reactive — it's looking at you, responding to you.
Color system
Scene background: #070710 (near black, slightly blue-shifted)
Primary accent: #6366f1 → #a855f7 (indigo to violet gradient)
Current Self state: Indigo/violet palette — cool, present-tense
Goal Self state: Amber/gold palette (#f59e0b → #f97316) — warm, aspirational
Success / achieved: Emerald #10b981
Glass panel — light mode: rgba(255,255,255,0.12) + backdrop-filter blur(28px) + 1px inset rgba(255,255,255,0.25) border
Glass panel — dark mode: rgba(255,255,255,0.07) + blur(28px) + 1px inset rgba(255,255,255,0.12) border
Typography: SF Pro (system-ui on macOS, Inter fallback on Windows/web). Numbers: tabular-nums, light weight for large values. Labels: 10px uppercase tracked 0.1em.
Motion system — spring physics
All layout transitions: Framer Motion spring — stiffness 200, damping 28, mass 1
Panel open/close: y: [30→0], opacity: [0→1], blur: [4px→0px]. Feels like a card lifting off a surface.
Metric number changes: Animated count-up/down with react-countup. 0.4s duration.
Body morph on metric change: GSAP to() on morphTargetInfluences values. Duration 0.6s, ease: power2.inOut. Only the affected zone morphs — others hold position.
Avatar camera: OrbitControls with damping 0.06. Camera position changes tween with GSAP, not snap. Auto-rotate at 0.003 rad/s when idle >10s.
Mode switch (Current ↔ Goal): Shared-element transition. The avatar scales down 0.95, cross-dissolves mesh state, scales back up. Background color transitions simultaneously. Duration: 0.7s.
Interaction design
Tap a body zone on the 3D model: Raycasting detects which named mesh was clicked (e.g. "waist_mesh", "chest_mesh"). Relevant metric input panel opens from the bottom. Camera smoothly zooms/tilts to that zone.

Slider interaction: Dragging a metric slider → the corresponding body zone animates in real time (GSAP morph tween on mouseMove, debounced 16ms). The model zone glows with a color overlay while being edited (warm amber for fat reduction zones, violet for muscle zones).

Long-press on avatar: Context menu appears: "Edit metrics / Switch to goal / Compare / Share / Reset to defaults"

Swipe left/right on avatar: Switches between Current Self and Goal Self with the shared-element transition.

Mouse cursor effect (desktop): Cursor position causes subtle parallax — avatar head tracks cursor (±8°), slight camera lean (±2°). Lusion-style "alive" feel.

Data architecture — stores, schema, flow
Two independent metric stores
currentMetrics (Zustand store + synced to DB):
All current-state measurements. Height, weight, all circumferences, all appearance metrics. This drives the Current Self avatar.

goalMetrics (Zustand store + synced to DB):
All goal-state measurements. Inherits missing values from currentMetrics (you don't need to re-enter height for your goal). Only delta values are stored — if a goal metric equals the current metric, it's null in DB. This drives the Goal Self avatar.

avatarPreferences (Zustand store):
Outfit, hair, accessories, camera position, lighting mode. Not body measurements — appearance choices.
Database schema (additions to existing)
user_metrics table: user_id, session_date, height_cm, weight_kg, age, gender, ethnicity_code, body_fat_pct, chest_cm, waist_cm, hip_cm, underbust_cm, shoulder_width_cm, torso_length_cm, upper_arm_cm, forearm_cm, wrist_cm, arm_length_cm, thigh_cm, knee_cm, calf_cm, ankle_cm, inseam_cm, foot_size_eu, neck_cm, face_shape_code, muscularity_chest, muscularity_arms, muscularity_legs, muscularity_core, muscularity_back, skin_tone_hex, hair_style_code, hair_length_code, hair_color_hex, hair_texture_code, beard_style_code, beard_color_hex, eyebrow_thickness, outfit_code

user_goals table: user_id, goal_type (workout/diet/surgery/style), target_weight_kg, target_body_fat_pct, target_waist_cm, target_chest_cm, target_muscularity_chest, target_muscularity_arms, target_muscularity_legs, target_muscularity_core, surgery_type_code, goal_hair_style_code, goal_hair_color_hex, goal_outfit_code, created_at, target_date

Blendshape weight computation — where it runs
All computation is client-side (browser/Electron). No backend API call needed to render the avatar. The mapping function (metric → blendshape weight) is a pure JS module (~200 lines of math). It runs on every slider drag event, batched via requestAnimationFrame. GSAP handles the smooth animation from current weight to target weight.
Gender, anatomy and privacy — the complete rules
Base mesh selection — gender is a mesh decision
Architecture rule
Gender (Male / Female / Other) is selected at onboarding. "Other" lets the user choose which base mesh they prefer, then apply any blendshapes from either set.

Gender selection is not a preference — it determines which GLB file loads (male_base.glb or female_base.glb). This cannot be changed without confirming a mesh reset (metric data is preserved, avatar restarts from the new base).
Anatomy — what is shown and when
Default state — always appropriate
By default, the model is clothed. Default outfit on first load is sport wear (shows body shape well, always tasteful).

Underwear mode: Available in settings under "Body view" → "Detailed body composition view." Requires confirming gender in profile. Shows gender-appropriate underwear mesh — fitted briefs (M), bra + briefs (F). This is the minimum clothing level at all times. No nudity, ever.

Why underwear mode exists: It's the only way to accurately visualize body fat distribution in all zones (thighs, glutes, abdomen, chest). Fitness apps that only show clothed models lose this accuracy. This is the same standard as medical body composition tools.
Female-specific anatomy handling
Breast volume blendshapes: Driven by chest circumference (bust) and underbust circumference, computing cup size equivalent (bust − underbust in cm → volume). 6 blendshape levels (0→5). These affect silhouette and proportion, visible in underwear mode as a bra-enclosed form. Always tasteful — this is body composition data, not explicit content.

Hip and glute blendshapes: Driven by hip circumference and body fat %. Gynoid fat distribution (female typical) deposits more in hips, glutes, thighs. The model reflects this correctly.

Female face: Different face baseline (softer jaw, different brow arch, different neck taper). Same face shape selector (6 options) but different base proportions.
Male-specific anatomy handling
Chest definition: Male chest has pectoral muscle definition blendshapes separate from female breast volume. These are driven by the muscularity slider, not circumference.

Android fat distribution: Male fat deposits preferentially in abdomen (belly, love handles). Above body fat threshold, belly_large and lovehandles_present blendshapes activate more aggressively than in female model.

Facial hair: Male model has a separate facial hair mesh layer. Stubble is a texture-based roughness overlay; beard variants are geometry meshes.

Male anatomy: Male underwear shows fitted briefs/boxers that are anatomically proportioned but non-explicit. The form is indicated by the silhouette and underwear mesh, not explicit geometry.
Data privacy
Body measurements are sensitive personal data. Architecture rules:
— All metric data encrypted at rest in DB
— No metrics visible in any share export (export = visual only)
— Local computation (no metrics sent to third-party APIs)
— User can delete all metric data at any time (full wipe)
— If app is used on shared device, avatar session can be PIN-locked
